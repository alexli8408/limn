# Deploying Limn

Three services: the Next.js app on Vercel, Postgres and Realtime on Supabase, the
OpenCV service on Render. UptimeRobot keeps the last one awake.

---

## 1. Supabase

Create a project, then from the repo root:

```bash
supabase init                                  # if supabase/config.toml is absent
supabase link --project-ref <your-project-ref>
supabase db push
```

Then in the dashboard:

- **Authentication → Providers → Anonymous sign-ins: enable.** This is the entire
  onboarding path. A visitor is drawing within one click, with no email step.
  Anonymous users are real rows in `auth.users`, so they own boards and can be
  upgraded in place if they later sign up.
- **Realtime private channels.** No toggle to hunt for on a current project:
  authorization *is* the RLS policies on `realtime.messages`, which migration
  `...000300_rls.sql` installs. What matters is that the client subscribes with
  `config.private: true`, which it does. Without that the topic string is
  unauthenticated and any signed-in user could subscribe to any board's channel
  by knowing its id.

Copy the project URL and the **anon** key from Settings → API. The anon key is
safe to expose; it only ever acts through RLS. Never put the service-role key
anywhere in this project. Nothing here needs it.

### Verifying the security properties

Before trusting the policies, run them:

```bash
./supabase/tests/run.sh
```

This applies every migration to a throwaway local database and asserts that a
stranger cannot see a board, that a share link grants access only once redeemed,
that a non-owner cannot change sharing settings, that direct snapshot writes are
refused, and that a stale writer's save is rejected rather than clobbering.

Worth running against plain Postgres rather than only against the hosted project:
a hosted Supabase project grants `anon`/`authenticated` broad default privileges,
which masks a migration that forgot to grant anything at all.

## 2. Render, the vision service

The repo has a blueprint. Dashboard → **New → Blueprint**, point it at the repo,
and it reads [`render.yaml`](../render.yaml).

Set one variable by hand:

- `ALLOWED_ORIGINS`: comma-separated, must include your Vercel production origin
  and any preview origins you use.

`VISION_API_KEY` is generated by Render. Copy its value; Vercel needs it.

Two things in the blueprint are deliberate:

- `PYTHON_VERSION=3.12.7`. `opencv-contrib-python-headless` 4.10 publishes wheels
  up to cp312; on 3.13 pip falls back to building OpenCV from source and the
  build times out.
- `--workers 1`. The free instance has a fraction of a vCPU. A second worker
  doubles memory for OpenCV without adding throughput.

Check it came up:

```bash
curl https://limn-vision.onrender.com/health
# {"status":"ok","service":"limn-vision","opencv":"4.10.0",...}
```

### 3. UptimeRobot, the keepalive

A Render free instance sleeps after 15 minutes idle and takes roughly 50 seconds
to cold start. That is fine for a background job and unacceptable for a user who
just tapped "trace my photo".

Create a monitor:

| Field | Value |
|---|---|
| Type | HTTP(s) |
| URL | `https://<your-service>.onrender.com/health` |
| Interval | 5 minutes |

Five minutes is the shortest free interval and comfortably inside the 15-minute
idle window. `/health` is the only unauthenticated route on the service,
specifically so this works without giving UptimeRobot a secret; it returns
uptime and a request count, so the monitor doubles as a liveness signal.

This does not eliminate cold starts. A deploy or a Render-side restart still
causes one. The client surfaces that honestly rather than hanging: the vision
proxy has a 55-second timeout and the UI says a sleeping instance can take ~50s.

## 4. Vercel, the app

Import the repo, then set **Root Directory** to `apps/web`. Vercel detects
Next.js and pnpm workspaces from there; the workspace packages are built by the
install step.

Environment variables (Production and Preview):

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | from Supabase → Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | from Supabase → Settings → API |
| `NEXT_PUBLIC_SITE_URL` | your deployment origin, e.g. `https://limn.vercel.app` |
| `GEMINI_API_KEY` | from [aistudio.google.com/apikey](https://aistudio.google.com/apikey) |
| `GEMINI_MODEL` | `gemini-2.5-flash` |
| `GEMINI_MODEL_PRO` | `gemini-2.5-pro` |
| `VISION_SERVICE_URL` | your Render URL, no trailing slash |
| `VISION_API_KEY` | the value Render generated |

`NEXT_PUBLIC_SITE_URL` matters: share links are built from it, so if it is wrong
every "Share" button copies a URL pointing at the wrong host.

Only the two `NEXT_PUBLIC_` variables reach the browser. `GEMINI_API_KEY` and
`VISION_API_KEY` are read through `serverEnv()`, which throws if called in the
browser, so importing it from a client component fails the build instead of
silently shipping a key.

## Order of operations

The dependencies run one way, so:

1. **Supabase** first, because everything needs the URL and anon key.
2. **Render** second, because Vercel needs its URL and generated key.
3. **Vercel** third.
4. **UptimeRobot** last, because it needs the live Render URL.
5. Go back to Render and put the real Vercel origin in `ALLOWED_ORIGINS`.

That last step is easy to forget. Without it the browser's preflight to the
vision service fails and photo vectorisation returns a CORS error that looks like
the service being down.

## What the free tiers actually allow

Worth knowing before a demo, and before running the load test.

| | Limit | What hits it |
|---|---|---|
| Supabase Realtime | 200 concurrent connections | one per open tab |
| Supabase Realtime | 2M messages/month | every *delivered* frame, so a broadcast to 10 peers is 10 |
| Supabase database | 500 MB | snapshots plus every 10th revision |
| Render | 750 instance-hours/month | UptimeRobot pinging keeps the clock running ~24/7 on one service |
| Vercel | 100 GB-hours of function time | the AI routes, which are the slow ones |
| Gemini | free tier is rate-limited per minute | a burst of beautify requests |

The message quota is the one that surprises people: `peers × rate × duration`
grows quickly. The load harness prints its projected message count before
starting and refuses runs over 200k without `--yes`.

Revision history is capped by design: a snapshot every 10th version, and only the
most recent 50 kept per board. Without that, a board autosaving every four
seconds would write ~900 revisions an hour.

## Troubleshooting

**`supabase db push` fails with `Connection terminated unexpectedly`.** Not auth,
and not provisioning. The direct host `db.<ref>.supabase.co` is IPv6-only; use
`./scripts/db.sh push`, which routes through the IPv4 pooler. Common on networks
without IPv6 and on fake-IP proxies, where a port check still succeeds against
the local proxy and so proves nothing.

**Subscribing fails with a policy error.** The `realtime.messages` policies did
not apply, or Realtime authorization is off in the dashboard. Check
`supabase/migrations/*_rls.sql` ran and that the client passes
`config.private: true`.

**A viewer's cursor never appears.** Expected. Viewers publish cursors as
presence state rather than broadcast, because the Realtime insert policy is split
by extension: editors may broadcast, viewers may not. That is deliberate. A
read-only collaborator could never persist elements, but without the split they
could still inject them into everyone's live canvas.

**Two peers both seem to be saving.** Also expected, briefly. Presence
propagation is not instantaneous, so during a reshuffle two peers can both
believe they are the elected writer. `save_board_snapshot` takes the version the
caller read as a precondition, so the loser is rejected as stale and retries
against the current version instead of reverting the winner's save.

**Photo vectorisation times out.** A cold Render instance. The first request
after a sleep pays ~50s; UptimeRobot prevents the sleep but not a post-deploy
cold start.

**The build fails on `serverEnv()`.** Something imported it from a client
component. That is the guard working. Move the call into a route handler or a
server component.
